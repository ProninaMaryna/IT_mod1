# Клієнт віддаленої папки з файлами (спрощений Google Drive)

## Огляд

Система — застосунок для роботи з віддаленою папкою файлів, спрощений аналог Google Drive. Тип задачі 2, варіант 12.

## 1. Автентифікація та простір користувача

- Застосунок забезпечує **автентифікацію на віддаленому сервері**.
- Після входу користувач потрапляє у свій особистий простір — **віртуальний диск**.

Користувач може:

- переглядати файли у своїй віддаленій папці;
- бачити атрибути файлу:
  - ім'я файлу;
  - дату й час створення;
  - дату й час зміни;
  - ім'я користувача, який вивантажив файл;
  - ім'я користувача, який останнім редагував файл;
- вивантажувати файли на сервер (зокрема перетягуванням, drag-n-drop);
- завантажувати файли з сервера;
- видаляти файли;
- синхронізувати обрану локальну папку з віддаленою.

## 2. Перегляд вмісту файлу

Після вибору файлу показується його вміст, якщо це файл одного з типів:

- **`.xml`** — як текст;
- **`.png`** — як зображення.

Для інших типів перегляд вмісту не передбачено: клієнт повідомляє про це і пропонує завантажити файл.

## 3. Стовпці таблиці

- Користувач може **показувати й приховувати** стовпці з інформацією про файл:
  - дата створення;
  - дата зміни;
  - хто вивантажив;
  - хто редагував.
- **Стовпець з ім'ям файлу видимий завжди.**

## 4. Операції

### Сортування

- Сортування за **датою і часом зміни файлу**.
- За зростанням (▲).
- За спаданням (▼).

### Фільтрація

- Показати **всі файли**.
- Показати лише файли типу:
  - `.java`
  - `.png`

### Приклад таблиці

| Ім'я | Створено | Змінено | Вивантажив | Редагував |
|---|---|---|---|---|
| `Main.java` | 2026-11-10 09:15 | 2026-11-12 18:40 | Maryna | taras |
| `diagram.png` | 2026-11-11 14:02 | 2026-11-11 14:02 | taras | taras |

Таблицю можна сортувати за стовпцем **Змінено** (▲/▼) і фільтрувати: **Усі / `.java` / `.png`**.

## 5. Архітектура

Стек: **Python (FastAPI)** на сервері, веб-клієнт на **Vue 3**, десктоп-клієнт на **PySide6 (Qt 6)**. Сервер і веб-клієнт розгортаються одним **Docker**-образом: публічно на **Render** або на власному ПК чи VPS через **Docker Compose**.

### 5.1 Компоненти

```text
       ┌──────────────────────┐        ┌───────────────────────┐
       │  Vue 3 (веб)          │        │  PySide6 (десктоп)     │
       │  клієнт у браузері    │        │  Windows / Linux / macOS│
       └──────────┬───────────┘        └───────────┬───────────┘
                  │ HTTPS (JSON/REST)               │ HTTPS (JSON/REST)
                  └────────────────┬────────────────┘
                                   ▼
                  ┌─────────────────────────────────┐
                  │  Docker-контейнер (Render)       │
                  │                                  │
                  │  FastAPI + uvicorn                │
                  │  app (HTTP) → services →          │
                  │  db / storage                     │
                  │  + роздача зібраного SPA (web/dist)│
                  └────────┬───────────────┬─────────┘
                           │               │
                ┌──────────┘               └──────────┐
                ▼                                     ▼
      ┌───────────────────┐               ┌────────────────────┐
      │  SQLite            │               │  Сховище файлів     │
      │  users, files,     │               │  локальний диск     │
      │  метадані          │               │  (data/blobs/),     │
      │                    │               │  за інтерфейсом     │
      │                    │               │  FileStorage        │
      └───────────────────┘               └────────────────────┘
```

Правила варіанта (перегляд, сортування, фільтр) і алгоритм синхронізації винесено в спільне ядро `cloudfolder/core`, яке використовують і сервер, і десктоп-клієнт. Веб-клієнт має їх дзеркальну реалізацію на JavaScript, що перевіряється тестами з тими самими даними.

### 5.2 Сервер (FastAPI)

- **Шари**: `app` (HTTP) → `services` → `db` / `storage`, тож бізнес-логіка (правила варіанта, права доступу, перевірка імен файлів) не залежить від HTTP і SQL.
- **База даних**: SQLite, без ORM: схема з двох таблиць невелика.
- **Автентифікація**: JWT (HS256, 12 год), ключ — у змінній `CLOUDFOLDER_SECRET`.
- **Паролі**: PBKDF2-SHA256 із сіллю.
- **Абстракція сховища**:

  ```python
  class FileStorage(ABC):
      def save(self, data: bytes) -> str: ...      # повертає ключ
      def load(self, key: str) -> bytes: ...
      def delete(self, key: str) -> None: ...
  # LocalFileStorage зараз; S3-сумісне сховище можна додати пізніше
  # з тим самим інтерфейсом, не змінюючи сервісів.
  ```

- **REST API**:

  ```text
  POST   /api/auth/register
  POST   /api/auth/login

  GET    /api/variant                          # правила варіанта, також health check
  GET    /api/files?sort=modified_at&order=asc&type=.java
  POST   /api/files                            # вивантаження (multipart); те саме ім'я = редагування
  GET    /api/files/{id}/content               # вміст для перегляду .xml / .png
  GET    /api/files/{id}/content?download=true # завантаження
  DELETE /api/files/{id}
  ```

### 5.3 Веб-клієнт (Vue 3)

- **Інструменти**: Vite + Vue 3 (Composition API, однофайлові компоненти), `fetch`.
- **Таблиця файлів**: сортування, фільтр і видимість стовпців — у модулі `lib/variant.js`.
- **Перегляд** у модальному вікні:
  - `.xml` — текст;
  - `.png` — зображення.
- **Синхронізація з браузера обмежена**: доступ до папки дає File System Access API (лише Chrome/Edge) після явного вибору папки, без фонового стеження. Тому веб-клієнт має кнопку «Синхронізувати зараз» і періодичний режим, поки вкладка відкрита.

### 5.4 Десктоп-клієнт (PySide6)

- **Інтерфейс**: Qt 6, шаблон MVVM: `viewmodel` не залежить від Qt-віджетів і тестується без GUI.
- **Мережа**: `httpx`, той самий REST API, що й у веб-клієнта.
- **Перегляд** у бічній панелі поруч із таблицею.
- **Тут працює повноцінна синхронізація**:
  - `QFileSystemWatcher` стежить за обраною папкою;
  - після змін (із затримкою 1,5 с, щоб не спрацювати посеред запису) і за таймером (кожні 15 с) обчислюється маніфест `{ім'я → SHA-256}`;
  - `plan_sync` порівнює його з віддаленим списком і станом минулої синхронізації та повертає дії;
  - клієнт виконує дії й показує їх у журналі синхронізації.

### 5.5 Зберігання даних

- **SQLite**: метадані (`users`, `files`) у каталозі `CLOUDFOLDER_DATA`.
- **Файли**: вміст у `data/blobs/` під випадковими ключами (UUID), окремо від бази; запис атомарний.
- **Docker Compose**: дані в іменованому томі `cloudfolder-data` і зберігаються між перезапусками.
- **Render (безкоштовний тариф)**: диск тимчасовий, дані зникають після перезапуску. Для постійного зберігання — Docker Compose або платний диск Render.

### 5.6 Розгортання

```yaml
# render.yaml
services:
  - type: web
    name: cloud-folder
    runtime: docker
    plan: free
    healthCheckPath: /api/variant
    envVars:
      - key: CLOUDFOLDER_SECRET
        generateValue: true
```

- **Render**: New → Blueprint, конфігурація з `render.yaml`. Кожен push у `main` перерозгортає сервіс. Публічна адреса: https://cloud-folder.onrender.com.
- **Docker Compose**: `docker compose up -d --build` на будь-якому ПК чи VPS.
- **Dockerfile** двоетапний: спершу збирається веб-клієнт (Node), потім сервер на Python роздає і API, і зібраний SPA з однієї адреси.
- **CI** (GitHub Actions): pytest, Vitest, збірка SPA і smoke-тест Docker-образу на кожен push.

## 6. Синхронізація

Синхронізація — це **тристороннє порівняння** локальної папки, віддаленої папки і стану після попередньої синхронізації. Вона запускається вручну, за таймером і (у десктоп-клієнті) за подіями файлової системи.

### 6.1 Що порівнюється

Три знімки виду `{ім'я → SHA-256}`:

- **local** — поточний вміст локальної папки;
- **remote** — поточний список файлів на сервері;
- **base** — стан після попередньої успішної синхронізації, зберігається у файлі `.cloudfolder-sync.json` у самій папці.

### 6.2 Можливі дії

| Локально | На сервері | Дія |
|---|---|---|
| новий або змінений | без змін | `upload` |
| без змін | новий або змінений | `download` |
| видалений | без змін | `delete_remote` |
| без змін | видалений | `delete_local` |
| змінений | змінений (по-різному) | `conflict` |
| однаковий | однаковий | нічого |

### 6.3 Видалення

Відсутність файлу локально може означати «ще не завантажено» або «користувач видалив». Розрізнити ці випадки дозволяє **base**: якщо файл був у минулій синхронізації і зник локально, його видалено, і видалення переноситься на сервер. Якщо файл видалено з одного боку, а з іншого змінено, зміна важливіша: файл відновлюється.

### 6.4 Запуск синхронізації

- **Десктоп-клієнт**: `QFileSystemWatcher` реагує на зміни в папці з затримкою 1,5 с; додатково таймер кожні 15 с підхоплює зміни на сервері.
- **Веб-клієнт**: кнопка «Синхронізувати зараз» і періодичний режим (кожні 10 с), поки вкладка відкрита.

### 6.5 Конфлікти

Якщо файл змінено з обох боків, жодна версія не перезаписується мовчки: зберігаються **обидві**. Локальна версія зберігається як копія з ім'ям на кшталт `report (конфлікт).xml` (і в папці, і на сервері), а віддалена версія залишається під початковим ім'ям.

### 6.6 Реалізація

```text
plan_sync(local, remote, base) -> [SyncAction(kind, name), ...]
```

Функція `plan_sync` (`cloudfolder/core/sync.py`, у веб-клієнті `planSync` у `web/src/lib/sync.js`) чиста, без вводу-виводу, тому повністю покрита модульними тестами. Дії виконує клієнт, після чого записує новий стан у `.cloudfolder-sync.json`.

### 6.7 Переносимість

Алгоритм синхронізації працює поверх звичайного REST API і не потребує окремого серверного протоколу. Тому будь-який новий клієнт (наприклад, консольна утиліта) може синхронізувати папку, не змінюючи сервер.
